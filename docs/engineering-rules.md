# Engineering rules

The package enforces shared C# style, build settings, and engineering rules.

Builds automatically apply the available source formatting and code fixes before compilation. A packaged task hosts Roslyn inside MSBuild using the current project's source files, references, language version, conditional symbols, analyzer configuration, and additional files. It does not launch a shell, `Exec` task, `dotnet format`, or any other child process. The task loads that Roslyn from the building SDK, so the analyzers and code fixes the SDK ships always run on the compiler they were built against, and standard C# code-fix providers come from the same place. The task assembly and shared configuration are resolved relative to the package, and the Roslyn directory is selected automatically from the SDK; consumer properties cannot redirect these paths. A copy of Roslyn also ships with the package and hosts the formatter when the SDK supplies none, and an analyzer that copy refuses because it references a newer compiler is constructed directly rather than dropped, with anything that still cannot run named in the build log.

The task applies supported project-wide fixes (or individual fixes when necessary) and repeats until stable. Generated files and design-time IDE builds are excluded. A file counts as generated exactly when the analyzers skip it: by its name (such as `.g.cs` or `.designer.cs`), by an `<auto-generated>` comment opening it, or by `generated_code` in configuration. Quoting the marker anywhere else, such as in a string, does not make a file generated. A project-wide fix that would also rewrite a generated file gives way to the individual fix. Unchanged source files keep their timestamps. Formatting of shared source directories is serialized to protect parallel and multi-target builds, and each target uses its own conditional symbols. Rules without a fix still fail compilation; fixes that add/remove documents or require project-system/UI operations are not applied automatically. No compiler diagnostic that fails the build is ever fixed automatically, because the available fixes declare API the author never wrote, add casts, and leave `NotImplementedException` bodies, which turns a compiler error into a run-time failure; every such diagnostic remains an ordinary compiler error, including the cases a missing `using` directive, a missing overload, or an explicit conversion would resolve. A compiler suggestion the build never fails for, reported as `hidden` or `info` rather than escalated to an error, is still a style concern and keeps its fix. The SDK's populate-switch suggestions (`IDE0010`, `IDE0072`) are suppressed as `NETAGENTS1001` and `NETAGENTS1002` when the switch already routes the remaining enum members through a `default` label, a discard arm, or an unconditional `var` pattern: the fix inserts its cases ahead of that arm, so the new empty `break` or `NotImplementedException` body would shadow the one that handled them. A switch with no such arm is not exhaustive, so it still reports and is still fixed. A language version the hosting Roslyn does not recognize — a newer SDK's default, such as C# 15 on `net11.0` — formats with that Roslyn's preview grammar instead of failing the build, while a value that is no language version at all fails with the property, value, and project named and remains the compiler's `CS1617`. A code-fix provider that cannot run — for example one built against a different Roslyn version than the hosting SDK — is skipped instead of failing the build, and any diagnostic it leaves behind still fails compilation. An action offered for a `hidden` or `info` suggestion is dropped the same way when applying it would introduce compiler errors, so an SDK suggestion cannot break a build that has nothing else wrong with it; a compiler-breaking action still fails the build when the diagnostic it repairs is a warning or an error. A dropped suggestion is never reported as the reason a run stopped: when only diagnostics without an applicable fix remain, the formatter keeps the rewrites it made and the compiler reports those diagnostics itself, and a failure the formatter does report names the blocking source errors. An individual fix may still introduce an error a later pass repairs, so only the state a run settles in decides: a run that would leave behind errors it introduced keeps none of its rewrites, writes nothing, and names those errors and the action that caused them instead: each error with the file, line, and column it would appear at in the formatted text, and that line as formatting would have written it. Formatting also adds time to the build and can apply style changes beyond whitespace.

The formatting task checks its inputs on every build that is not a design-time IDE build, and there is no property that turns enforcement off. A completed run can be reused when a persisted SHA-256 fingerprint matches the complete formatting inputs: authored and generated source contents and paths, item metadata (including links and reference aliases), references, analyzer and code-fix assemblies and their loadable dependencies, SDK and packaged formatting hosts, configuration and additional files, project/import/package inputs, and evaluated language/compiler/build settings. Content changes invalidate the record even if file sizes and timestamps are preserved; adding, removing, or renaming inputs also invalidates it. The record describes the final rewritten sources, is stored atomically under the target's intermediate directory, and is removed by `dotnet clean`. Missing or corrupt records trigger full formatting. Runs with blocking source diagnostics or analyzer faults do not publish a record. Shared-source locking covers both the cache check and formatting, and each target framework/configuration uses its own record. Policy validation and compiler enforcement remain active on unchanged builds.

This repository uses the same task, with an isolated copy of the locally built task to allow it to rebuild itself. On the first clean checkout, the task project must bootstrap before the formatter becomes available. The bootstrap condition and local code-fix loading live only in the repository's `Directory.Build.targets`; the packaged targets always run formatting on builds that are not design-time IDE builds.

Source parsing errors stop formatting before analyzers or code-fix providers are loaded, with the source paths and compiler diagnostics reported immediately. Correct the syntax before the build applies style fixes. On valid syntax, fixes for warnings and errors run before optional suggestions. Each candidate is formatted before validation, and the accepted project's diagnostics carry into the next pass. Compiler-breaking candidates are rejected before running analyzers; a rejected optional candidate can reuse its validation only when its complete source state is unchanged and the rejecting errors are still new relative to the current project. Changes to another file require validation again. Progress messages name each pass and action and include elapsed time.

Only code-fix exports declaring C# support are composed, including providers shared with other languages. Reusing completed formatting also avoids repeating rejected optional fixes on unchanged builds. To profile a build, collect a trace with `dotnet-trace`, which measures the formatter as a whole, including the code fixes an analyzer-only measurement cannot see. `dotnet clean` discards the completion record when a full run is wanted.

## Diagnostics

Every custom diagnostic is an error and is marked non-configurable.

| Diagnostic | Meaning |
| --- | --- |
| NETAGENTS0001 | Reject implicit and explicit boxing conversions, including nullable values, enums, interface conversions, and unconstrained generics. |
| NETAGENTS0002 | Reject explicit `object`/`dynamic` type uses, untyped arrays/generic collections, and untyped values returned by calls, fields, properties, indexing, and await. Overrides and explicit interface implementations keep the prescribed parameter and result types of the signature they inherit; their bodies are still checked. |
| NETAGENTS0003 | Reject C# `lock` statements. |
| NETAGENTS0004 | Reject catch blocks containing no executable statements, including comment-only blocks. |
| NETAGENTS0005 | Reject single-letter declarations, uppercase acronyms, and known abbreviated identifier words. Standard `I…` and `T…` prefixes and the .NET `Async` naming convention (for example, `ReadAsync`) are supported. |
| NETAGENTS0006 | Require one top-level type per file with the matching case-sensitive file name. Appropriate nested types are allowed. |
| NETAGENTS0007 | Reject the postfix null-forgiving operator. |
| NETAGENTS0008 | Reject literal-true `while`/`do` conditions and conditionless or literal-true `for` loops. |
| NETAGENTS0009 | Require parameter names for inline literal, `default`, and collection expression arguments in methods, constructors, delegates, and indexers, including signed/parenthesized literals but not a value another operator produces such as `^1` or `~0`, and omit names the rule does not require. For expanded `params`, pass a named collection. Attributes use their separate language syntax. Includes an automatic code fix and Fix all support. |
| NETAGENTS0010 | Require authored source files to contain fewer than 1,000 lines besides comments. Lines holding only comments of any kind (`//`, `/* */`, `///`, and `/** */`) are not counted, nor is any line inside a block comment, blank ones included; lines holding code next to a comment and blank lines outside comments count. The required final newline terminates the last line instead of starting another one. |
| NETAGENTS0011 | Reject type names matching containing namespace segments or feature directories below the project root. |
| NETAGENTS0012 | Reject framework synchronization types and blocking task/thread waits, including aliases, static imports, and explicit awaiter `GetResult` calls. |
| NETAGENTS0013 | Reject changes to the effective shared configuration and diagnostic severities. |
| NETAGENTS0014 | Reject incompatible project settings. This diagnostic comes from the package's MSBuild target. |
| NETAGENTS0015 | Require return values to be consumed. Reject ignored non-void calls, ignored awaited results, and assignments to `_`, including named underscore symbols. Reject deconstruction discards, including `foreach` and `await foreach`. This includes conditional calls, expression-bodied members, callbacks, and `for` clauses. |
| NETAGENTS0016 | Require blank lines before and after control-flow statements and multiline local declarations when another statement is adjacent. Includes an automatic code fix and Fix all support. |
| NETAGENTS0017 | Omit optional braces around one single-line body statement; require braces for multiline bodies and keep conditional chains consistent. A statement block that keeps its braces puts `{`, each statement, and `}` on lines of their own, empty blocks included. Includes an automatic code fix and Fix all support. |
| NETAGENTS0018 | Allow at most 16 authored C# files directly in each directory per project. Organize larger directories into subdirectories with narrower responsibilities. |
| NETAGENTS0019 | Require single-line conditions of at most 128 characters in `if`/`else if`, `while`, `do`, `for`, ternary expressions, catch filters, and switch `when` guards. Extract longer conditions into a separate variable declaration. |
| NETAGENTS0020 | Keep argument and parameter lists on one line when their compact contents are at most 128 characters; otherwise keep the first item beside the opening delimiter, put each later item on a line of its own one level deeper, and close the list right after the last item. Includes an automatic fix and Fix All support. |
| NETAGENTS0021 | Require a blank line between adjacent method declarations, including constructors, destructors, and operators. Includes an automatic fix and Fix All support. |
| NETAGENTS0022 | Organize the members of every type: order them by kind, visibility, const/static/instance, members fixed once construction ends (readonly fields; get-only, `init`, `required`, and computed properties) before settable ones, then ordinal name, and separate their groups with one blank line and none inside a group. Single-line fields, properties, and events of one bucket group together; methods, constructors, nested types, and members spanning lines or carrying documentation or attributes stand alone; a comment line opens a new group and heads a section whose members stay below it. Includes an automatic fix and Fix All support. |
| NETAGENTS0023 | Forbid blank lines directly after an opening brace or before a closing brace, in every block: type bodies, method and statement blocks, accessor lists, namespaces, enums, switch bodies, initializers, lambdas, and local functions. Includes an automatic fix and Fix All support. |
| NETAGENTS0024 | Reject tuple result contracts, including C# tuples, `System.ValueTuple`, `System.Tuple`, and tuples nested inside asynchronous or other wrapper types. Return a dedicated named record, class, or struct instead. |
| NETAGENTS0025 | Require one `<summary>` element per documentation comment, so a declaration is described once. Describe parameters, results, and detail with `<param>`, `<returns>`, and `<remarks>` instead. |
| NETAGENTS0026 | Omit the optional parentheses around a lambda's single inferred parameter. Includes an automatic fix and Fix All support. |
| NETAGENTS0027 | Import a type's namespace and name the type directly instead of writing it fully or partly qualified, whether as a type name or at the start of an expression such as `System.Math.Min(first, second)` or `System.StringComparison.Ordinal`. Includes an automatic fix and Fix All support, except where the name is already taken. |
| NETAGENTS0028 | Require a `<summary>`, `<param>`, or `<typeparam>` element to say something the name it describes does not already say, and a `<returns>`, `<value>`, `<exception>`, or `<remarks>` element to say anything at all. A description built only from the name's own words, from documentation boilerplate, or left empty is rejected. Comments carrying `<inheritdoc>` are exempt. No automatic fix: the wording is the author's. |
| NETAGENTS0029 | Require documentation prose to sit inside an element. Text written between or before elements never reaches the generated documentation, so it is wrapped in `<summary>`. Comments carrying `<inheritdoc>` may still add a note. Includes an automatic fix and Fix All support. |
| NETAGENTS0030 | Require overloads sharing a name to carry different `<summary>` text, so a reader choosing between them learns which to call. Members of different types may describe themselves identically. No automatic fix: the distinction is the author's to state. |
| NETAGENTS0031 | Reject a method declaration whose name ends with its first parameter's whole name: `UpdateValue(int value)` should be `Update(int value)`, and `GetAppStoreId(string appStoreId)` should be `Get`. Names are compared word by word, ignoring case. A name that shares only some of the parameter's words is accepted, since it names something else: `GetApp(string appStoreId)` gets an app and `GetFileId(string appStoreId)` gets a file's id. Only declarations are checked; what a caller passes, or what its variables are called, does not matter. An `Async` suffix is ignored, and a name made of nothing but the parameter's words, such as a one-word name, is exempt. An override, an interface implementation, a partial method's implementation, and an `extern` method take their name from elsewhere and are not reported; an interface member declared in the project is reported on the interface. No automatic fix: renaming the method or the parameter is the author's call. |
| NETAGENTS0032 | Reject numeric casts of values computed at run time, such as `(int)value` or `(byte)(first + second)`; convert with `CreateChecked`, `CreateSaturating`, or `CreateTruncating` so the code says what happens to a value out of range. Implicit conversions are the language's own and are never reported, including the widening C# applies to the operands of `==`, `<`, `+`, `-`, `<<`, and compound assignments. Constants, `char` code points, nullable, enum, and user-defined conversions, expression trees, and target frameworks without generic math are left alone. Includes an automatic fix and Fix All support that keeps each cast's behavior: a cast that could have been implicit, a cast in a `checked` context, and a cast to or from `decimal` become `CreateChecked`, and any other cast becomes `CreateTruncating`. |
| NETAGENTS0033 | Require the documentation of a public or protected member to carry every tag its signature calls for: a `<param>` for each parameter of a method, constructor, indexer, delegate, operator, record, or primary constructor; a `<typeparam>` for each type parameter; `<returns>` for any result, including `Task<T>` and `ValueTask<T>`; `<value>` on properties and indexers; and an `<exception>` for each exception the member's own body throws, through `throw` or a throw helper such as `ArgumentNullException.ThrowIfNull`. A documented base exception covers the ones derived from it, and exceptions the body catches, rethrows, or leaves to a lambda are not counted. Comments carrying `<inheritdoc>` or `<include>` are exempt. No automatic fix: the text is the author's. |
| NETAGENTS0034 | Reject tags that do not fit a public or protected member: `<returns>` where nothing is returned (`void`, a `Task` or `ValueTask` without a result, a constructor), `<value>` outside properties and indexers, `<param>` and `<typeparam>` out of declaration order, `<inheritdoc>` without a `cref` on a member that overrides and implements nothing, and leftover `<placeholder>` elements. Includes an automatic fix and Fix All support that removes the misplaced tags and placeholders and reorders the parameter tags; an `<inheritdoc>` with nothing to inherit is reported only, since its text is the author's. |
| NETAGENTS0035 | Require the tags documenting one public or protected member to say different things: two tags carrying the same text, compared without case, layout, or a closing full stop, are reported. No automatic fix. |
| NETAGENTS0036 | Require the text of a public or protected member's `<summary>`, `<param>`, `<typeparam>`, `<returns>`, `<value>`, `<exception>`, and `<remarks>` to end with a full stop, question mark, or exclamation mark. Text closing on a list, a code block, or a table is left alone, and a closing `<para>` is judged by its own last sentence. Includes an automatic fix and Fix All support. |
| NETAGENTS0037 | Require public and protected summaries to open as the .NET API documentation does: a property with "Gets", "Sets", or "Gets or sets" to match the accessors a caller outside the assembly can use ("Gets or initializes" is accepted for `init`), and a constructor with "Initializes a new instance of the `<see cref="T"/>` class", "struct", or "record". Includes an automatic fix and Fix All support for constructors, which replaces an opening written another way or places the standard sentence before the author's text; property summaries are reported only. |
| NETAGENTS0038 | Require `null`, `true`, and `false` in public and protected documentation text to be written as `<see langword="…"/>`, including a `<c>` element holding only the keyword, and a Boolean `<returns>` or `<value>` to read "`<see langword="true"/>` if …; otherwise, `<see langword="false"/>`." Keywords inside code and hyphenated prose such as "non-null" are left alone. Includes an automatic fix and Fix All support for keywords; Boolean wording is reported only. |
| NETAGENTS0039 | Require the statements of every block to sit in groups of one kind, with one blank line between groups and none inside a group. Declarations, declarations of awaited results (`string text = await reader.ReadToEndAsync();`), assignments (including compound assignments, increments, and decrements), assignments of awaited results (`text = await reader.ReadToEndAsync();`), event subscriptions (`+=` and `-=` on an event), calls, await statements, and argument checks (static `ThrowIf…` calls on `ArgumentException` and the types deriving from it) each form groups of their own. A comment line starts a new group, with the blank line above the comment; a comment sharing a statement's line does not. Every statement written over several lines stands alone, whatever its kind, so two multiline statements never share a group, and so does every other statement, as `NETAGENTS0016` keeps control flow and multiline declarations. Method, constructor, operator, accessor, lambda, anonymous method, local function, nested block, switch section, and top-level statement lists are all covered. Includes an automatic fix and Fix all support that only moves blank lines. |
| NETAGENTS0040 | Allow at most four statements in a group of `NETAGENTS0039`, and at most four fields, properties, or events in a group of `NETAGENTS0022`, so a longer run is split by comment lines that say what each part is for. A blank line does not end a group, since the formatter removes it. Runs of argument checks, and constructor runs where every statement stores a parameter as it is (`Price = price;`), are exempt. There is no automatic fix: the message asks for one short sentence above each part that says what the part achieves or why it is needed, not what the code already says. |
| NETAGENTS0041 | Keep the `when` keyword on the line of the clause it guards: `catch (IOException exception) when (…)`, `case int count when count > 0:`, and `int count when count > 0 => …` in a switch expression. A `when` that starts a line of its own is reported. Includes an automatic fix and Fix All support that moves `when` up behind the clause with one space; when a comment stands between the two, the rule reports without a fix so the author decides where the comment goes. |
| NETAGENTS0042 | Write a field, property, event, method, constructor, operator, or indexer on one line when it is wrapped only at the `=` of its initializer or the `=>` of its expression body and the whole member fits within 128 characters. A member that spans lines anywhere else is left to the rules for its argument lists, initializers, and lambdas, and a comment beside the operator keeps it wrapped. Includes an automatic fix and Fix All support. |
| NETAGENTS0043 | Reject suppressions written into the code for the rules the build requires: `[SuppressMessage]` and `[UnconditionalSuppressMessage]` on any member or the assembly, and `#pragma warning disable`, when they name a NetAgents rule, a code analysis (`CA`) rule, a code style (`IDE`) rule, or `CS1591`, and a bare `#pragma warning disable` that silences every warning. Together with `NETAGENTS0013` and `NETAGENTS0014`, which reject configuration and project-file suppressions, this leaves changing the code as the only way through. Suppressions of other analyzers stay available. |
| NETAGENTS0044 | Reject reading a member of a parenthesized `await`, as in `(await client.GetAppAsync(id)).Versions`, whether by member, element, or conditional access. Store the awaited value in a local named for what it is and read its members from there, which keeps the expression on one line and says what the value is. No automatic fix: the name is the author's to choose. |
| NETAGENTS0045 | Write a declaration, expression statement, `return`, `throw`, or `yield return` on one line when it spans lines and the joined statement fits within 128 characters, including its indentation: a chain broken before each dot, parentheses on lines of their own, and a split ternary are joined. A statement holding a lambda with statements, a switch expression, a comment, or a string spanning lines is left to the rules for those. Includes an automatic fix and Fix All support, which joins the lines and lets the formatter settle the spacing. |
| NETAGENTS0046 | Reject local names built only from placeholder words: every word one of `is`, `condition`, `met`, `result`, `flag`, `temp`, or a number, as in `result`, `flag`, `temp`, `isConditionMet`, `result2`, or `tempResult`. Local variables, `foreach` and `catch` variables, and variables declared in patterns, `out` arguments, and deconstructions are covered; parameters, fields, and properties are not. No automatic fix: the message asks for a name that says what the value is or means, such as `hasNoVersions` or `selectedApp`. |

Condition length counts source characters, including spaces and comments, between condition parentheses (excluding the parentheses). For `for`, only the condition between semicolons is checked; for ternaries, only the condition expression is checked (`?` and `:` branches may span multiple lines); for `when` guards, the text after `when` through the condition is checked. Newlines immediately inside condition parentheses are also forbidden. Extraction is manual: preserve evaluation frequency and short-circuit behavior, especially in loops.

Argument layout covers method and delegate calls, constructors (including target-typed `new`, `base`, and `this` initializers), attributes, element access, and declaration parameters for methods, constructors, primary constructors, records, delegates, operators, indexers, local functions, and anonymous functions. Generic type argument lists and collection initializers are not included. The shared 128-character limit counts the normalized single-line contents, including commas and spaces, but excludes delimiters, the method/type name, and indentation. An expanded list keeps its first item on the line of the opening delimiter, starts each later item on a line of its own, indented one level deeper than the line the list starts on, and closes right after the last item. A list nested in the first item of another list that opens on the same line and continues past it goes one level deeper still, so the two lists never share an indentation. A comment between a delimiter and its neighbouring item keeps them on separate lines instead. A single item longer than the limit stays where it is, since there is nothing to split it from; this rule does not split literals or expressions.

```csharp
internal static Task<int> RunDevelopmentKit(string workingDirectory,
    string[] arguments,
    string? expectedDiagnosticIdentifier = null,
    string[]? expectedOutput = null,
    bool withoutShell = false)
{
    return Task.Run(() =>
    {
        Prepare(workingDirectory, withoutShell);

        return Execute(arguments, expectedDiagnosticIdentifier, expectedOutput);
    });
}

context.RegisterCodeFix(CodeAction.Create(title: "Fix argument and parameter layout",
        cancellationToken => FixArguments(context.Document, diagnostic.Location.SourceSpan, cancellationToken),
        nameof(ArgumentLayoutCodeFixProvider)),
    diagnostic);
```

Multiline literals and comments that cannot safely fit on one line retain their contents and use expanded layout even below the limit. So does a list holding a lambda or anonymous method whose body has two or more statements, or holds a block or switch section that does: each of those statements goes on a line of its own, and the body opens on its own line, indented as deep as the line the lambda starts on. On one line those statements would sit where `NETAGENTS0016` puts blank lines, and the two rules would undo each other on every pass. A lambda whose body is one statement still collapses. Lists containing preprocessor directives are left unchanged. Conditions still independently satisfy `NETAGENTS0019`; extract a call into a variable if its expanded arguments would make a condition multiline.

Use **Fix argument and parameter layout** or run:

```bash
dotnet format analyzers --diagnostics NETAGENTS0020
```

Argument names converge on one shape: an inline literal, `default`, or collection expression
argument carries its parameter name, so `Execute([diagnostic])` becomes
`Execute(diagnostics: [diagnostic])`, and every other argument is positional. Only a sign or parentheses wrap a
literal, so an index from the end or a bitwise complement is a computed value and stays
positional; naming one would also be rejected outright by an implicit `Index` indexer. A name is only reported as unnecessary
when dropping it provably keeps the same binding — each argument already sits in its own
parameter slot, nothing is reordered, and no optional parameter is skipped — so
`Execute(first, third: third)` keeps its name. The fix rewrites a whole argument list at once,
re-resolves the call against the compiler before accepting the rewrite, and leaves line breaks,
indentation, and comments alone. Expanded `params` arguments become one named collection, so
`Log(1, 2)` becomes `Log(values: [1, 2])`; the normal form is untouched, because `Log(default)`
passes a null array rather than a one-element one. Shapes with no safe rewrite stay reported and
unfixed: `dynamic` calls, `__arglist`, function pointers, argument lists containing preprocessor
directives, a `params` collapse that would drop a comment or sits inside an expression tree, and
any rewrite that would bind to a different overload. Longer names can push a call past the
`NETAGENTS0019` condition limit, which has no fix and needs the variable extraction described
above. Run:

```bash
dotnet format analyzers --diagnostics NETAGENTS0009
```

Directory limits count each distinct `.cs` file included in the project once,
including linked source files in their physical directories. Generated files
are excluded, and each subdirectory is counted separately. The seventeenth
authored file causes a build error that names the directory and its file count.
Split oversized directories by feature or responsibility to resolve it.

Statement spacing covers `if`, loops, `switch`, `try`, `using` (including
declarations), `return`, `throw`, `break`, `continue`, and `yield`. Multiline
local declarations include chained calls, switch expressions, conditional
expressions, and object initializers. Single-line declarations can remain
grouped. Block edges stay unpadded, and unbraced bodies stay attached to their
controlling statement. Comments and existing line endings are preserved. Use the
editor's **Insert blank line between statements** quick fix or run:

```bash
dotnet format analyzers --diagnostics NETAGENTS0016
```

Statement groups (`NETAGENTS0039`) decide every other blank line between
statements. All blank lines inside a block are removed first, then one goes
wherever the group changes:

```csharp
ArgumentNullException.ThrowIfNull(cart);

Order order = new(cart.CustomerId);
decimal total = 0;

HttpResponseMessage response = await client.GetAsync(url);

order.Status = OrderStatus.Pending;
order.PlacedAt = clock.UtcNow;

await repository.SaveAsync(order, cancellationToken);

logger.LogInformation(message: "Placed order {OrderId}", order.Id);
```

A statement written over several lines, such as a call whose arguments go one
per line, is a group of its own, with a blank line on either side.

The fix never reorders statements, so a block whose kinds alternate gets a blank
line between every statement until its author regroups it. When a group grows
past four statements, `NETAGENTS0040` asks for a comment line above each part
that says what the part is for; the comment starts a new group. When the
formatter applies a suggestion that leaves blank lines where these rules no
longer want them, such as two separated `if` statements that become
`builder?.Length = length;` and `builder?.Capacity = length;`, it first settles
them with the layout fixes that change only whitespace, and judges the
suggestion afterwards. Run:

```bash
dotnet format analyzers --diagnostics NETAGENTS0039
```

`NETAGENTS0023` enforces unpadded block edges everywhere rather than merely
declining to add padding: a blank line directly after `{` or directly before `}`
is an error in every block, including type bodies, method and statement blocks,
accessor lists, namespaces, enums, switch bodies, object and collection
initializers, lambdas, and local functions. Blank lines inside comments and
string literals are untouched, blocks containing preprocessor directives are
skipped, and existing line endings are preserved because the fix only deletes.
Run:

```bash
dotnet format analyzers --diagnostics NETAGENTS0023
```

Brace style depends on the **body**, even when a loop header spans several
lines. Conditions must independently satisfy `NETAGENTS0019`. This covers `if`/`else`, `for`, `foreach` (including
`await foreach`), `while`, `do`, `using` (including `await using`), `fixed`, and
`case`/`default` bodies. A case with multiple statements also requires a block.
If any branch in an `if`/`else if`/`else` chain needs braces, every branch keeps
or gains them. Required language blocks, scope-dependent blocks, directives,
and braces protecting an `else` binding are preserved. Case wrapping preserves
variables and local functions shared with other sections.

A statement block that keeps its braces gives `{`, each statement, and `}` a
line of their own, empty blocks included. This covers the bodies above,
`try`/`catch`/`finally`, `checked`/`unchecked`, `unsafe`, and nested blocks.
Method, accessor, local-function, lambda, and anonymous-method bodies are
declarations rather than statements and keep the layout written. An unbraced
body goes on its own indented line below its header (`IDE2001`, set through
`csharp_style_allow_embedded_statements_on_same_line_experimental = false`), so
`if (ready) { return; }` and
`try { Run(); } catch (IOException exception) { Log(exception); }` become:

```csharp
if (ready)
    return;

try
{
    Run();
}
catch (IOException exception)
{
    Log(exception);
}
```

Use **Fix body braces** or run the following to add missing braces and remove
unnecessary ones:

```bash
dotnet format analyzers --diagnostics NETAGENTS0017
```

Check, return, pass, or store and use every returned value. For example, use
`if (values.TryGetValue(key, out var value))` to handle success and failure;
calling `TryGetValue` alone or assigning its result to `_` fails the build.
Storing a result without reading it also fails the build (`IDE0059`).
Every `_ = expression` is rejected, including constants, properties, object
creation, and awaited results. Naming a variable, parameter, field, or property
`_` does not bypass the assignment rule. Underscore variable initializers and
compound assignments are rejected too. Consume all deconstructed values,
including those bound by `foreach` and `await foreach`.
Calls returning `void` and awaited operations with no result (`Task` or
`ValueTask`) are allowed. Awaited `Task<T>` and `ValueTask<T>` results must be
consumed. Fluent and assertion APIs follow the same rule. An `out _` argument
does not discard a method's return value and remains allowed when that return
value is consumed.

Framework synchronization bans cover `Lock`, `Monitor`, `Semaphore`,
`SemaphoreSlim`, `Mutex`, reader/writer locks, spin locks/waits, reset events,
wait handles, `CountdownEvent`, and `Barrier`. `Interlocked`, `Volatile`,
cancellation, concurrent collections, and channels remain available.

A type is named directly rather than written with its namespace, whether the reference is fully or
only partly qualified, and whether it is a type name or the start of an expression: a static call
such as `System.Math.Min(first, second)`, a static member such as `System.StringComparer.Ordinal`,
an enum value, or the containing type of a nested one, as in `System.Environment.SpecialFolder`.
The rule reports a reference only after proving the short form binds to that same type and that
importing its namespace leaves every other name in the file bound as it was, so an accepted fix
cannot change what the code means. In an expression the short name must also be free of locals,
parameters, and members, since those are found before types: in a class with a `Directory`
property, `System.IO.Directory.GetFiles(…)` cannot become `Directory.GetFiles(…)`. A value of the
type's own name and type is no obstacle, because C# still reads `Status.Active` as the type when a
`Status` property of type `Status` is in scope. Namespace
declarations, `using` directives, `nameof`, alias-qualified names, and qualification by a containing
type are left alone. Where the short name already refers to something else, only a `using` alias
can shorten the reference, and naming that alias renames a type for the whole file; the rule
reports those references and leaves the choice to the author rather than inventing a name. The import is placed with the other
directives: `System` first, then ordinal order, aliases last. Use **Import the type's namespace** or
run:

```bash
dotnet format analyzers --diagnostics NETAGENTS0027
```

A lambda with one inferred parameter is written without parentheses. They are only optional in that
one shape, so an empty or multi-parameter list, an explicit parameter type, an attribute, a modifier
such as `ref`, a default value, and an explicit return type all keep them. The fix drops the
whitespace that padded the parentheses and keeps any comment written between them. Use **Drop the
lambda parameter parentheses** or run:

```bash
dotnet format analyzers --diagnostics NETAGENTS0026
```

A documentation comment describes its declaration once. Consecutive comment lines parse into a
single comment, so a second `<summary>` stacked above a declaration does not document anything new:
the compiler accepts it silently and writes every one of them into the generated XML, where a member
is only allowed one. Each summary after the first is reported where it is written, so the extra text
can be moved into `<param>`, `<returns>`, or `<remarks>`, or deleted. Choosing which description to
keep is an editorial decision, so this rule has no automatic fix.

Result contracts use dedicated named types rather than tuples. This applies to methods,
local functions, properties, indexers, delegates, operators, function pointers, and
anonymous functions, including inferred lambda results and tuples nested inside
`Task`, `ValueTask`, collections, arrays, or custom generic wrappers. Overrides and
interface implementations may keep tuple results prescribed by their inherited
contracts. Tuple parameters, fields, locals, arguments, and deconstruction remain
available, as does consuming a tuple returned by a dependency without returning it
again. Choosing the appropriate result type is a design decision, so this rule has no
automatic fix.

The naming vocabulary includes `args`, `cfg`, `ctx`, `config`, `dto`, `dsp`,
`msg`, `sdr`, `sql`, `tmp`, and other common shortened words; see
`Naming/DescriptiveNameAnalyzer.cs` for the complete list. Common domain terms such as
`id`, `ids`, `html`, `json`, `api`, `http`, `https`, `tcp`, `udp`, `uri`,
`url`, `utf`, and `xml` stay available, though their uppercase spellings (`ID`,
`HTML`, `JSON`, `API`, `HTTP`) remain acronyms the rule rejects.
Framework-owned overrides and explicit interface implementations are exempt
from renaming their prescribed member names, and `NETAGENTS0002` likewise
accepts the `object` parameters and results those signatures prescribe. Referencing existing framework
names does not require renaming framework APIs.

## Documentation

The documentation rules exist so that a reader learns something a member's name and signature do not
already say. CS1591 makes a comment exist, NETAGENTS0033 makes it cover every parameter, result,
value, and thrown exception, and the remaining rules keep each tag in the right place, worded as the
.NET API documentation words it. None of that makes documentation useful by itself, and none of it
should be satisfied with boilerplate.

Write documentation by hand, for the people who will call the member:

- Say what actually happens: what the member does with its arguments, what state it reads or
  changes, what it costs, and what it hands back in the edge cases (nothing found, empty input,
  cancellation).
- Give each `<param>` the valid values, units or format, and what happens with an empty, missing,
  or out-of-range argument. Give each `<exception>` the exact condition that causes it.
- Use `<remarks>` for the behavior behind the member that a caller needs to rely on it, and an
  `<example>` with a short code sample wherever its use is not obvious.

Every report that asks for words says this in its message, because a rule can tell that a tag is
missing or empty, but only its author can make it worth reading. The rules that fix themselves only
rearrange or punctuate what was written; they never write descriptions.

## Automatic formatting and the public API

The formatter validates a candidate fix by reanalyzing the project it is
formatting. It runs before that project compiles, and the projects that
reference it are neither built nor visible, so a fix that changes what other
assemblies can name cannot be checked that way at all.

A fix is therefore refused when it moves a type to another namespace and the
file declares a type outside the assembly can name: one declared `public`, or
any top-level type when the assembly carries `InternalsVisibleTo`. In practice
this is `IDE0130`, "change namespace to match folder structure", which
otherwise renames public namespaces on the strength of a project that still
compiles on its own and breaks every project referencing it. The diagnostic is
still reported, so moving the file or the namespace stays an author's decision.
Internal types in an assembly that shares nothing are moved as before.

## Razor components and views

Razor compiles a component or view into generated C#, and copies the C# its
author wrote into it after `#line` directives that name the `.razor` or
`.cshtml` file. NETAGENTS0001 through NETAGENTS0005, NETAGENTS0007,
NETAGENTS0008, NETAGENTS0012, NETAGENTS0015, and NETAGENTS0024 check that
copied C#: the members of `@code` and `@functions` blocks, the statements of
`@{ }` blocks, and lambdas such as an `@onclick` handler. Their errors name the
Razor file and line, and none of them has an automatic fix, so each is fixed
by hand. A check applies to a statement, member, or lambda written whole in the
Razor file. An expression written in markup, such as `@count` or
`@item!.Name`, is an argument to a call Razor generates around it, so it is not
checked, and neither is control flow that wraps markup, such as `@foreach`.
The code Razor generates between those stretches is never checked. A
code-behind `.razor.cs` file is ordinary C# and meets every rule.

The other rules apply to C# files only. Formatting, ordering, and import rules
exist to be fixed during the build, and the build never rewrites a Razor file.
The file and structure rules would measure the generated file rather than the
one its author wrote, and the documentation rules read whole files and types,
which cannot be limited to the parts an author wrote.

The .NET code-quality and style analyzers (`CA…`, `IDE…`) skip generated code
by their own design, so they do not check Razor files either. Treating Razor's
output as authored code (`generated_code = false`) would aim them at the code
Razor generates as well: its `using` directives and namespace declaration, and
`ConfigureAwait` calls in components, where leaving the renderer's
synchronization context breaks rendering. The package does not change that
setting.

## Shared editor configuration

The shared C# preferences come from Microsoft's built-in
`dotnet new editorconfig` defaults for the SDK used to build each package
release. Updating the package picks up refreshed defaults. They apply globally
and automatically, with style and formatting violations treated as errors.
Every source file must end with a newline.
The template's generic type-parameter naming selector is corrected to
`type_parameter` so the conventional `T` prefix applies to type parameters.

Consumer editor and project settings must agree with the shared policy.
All .NET and code style analysis is enabled at the latest SDK level, with
warnings treated as errors during builds. XML documentation is generated;
public APIs require XML comments (`CS1591`), and unused imports and assignments
are errors (`IDE0005`, `IDE0059`). Disabling required analysis, documentation,
or severity settings fails the build with `NETAGENTS0014`.
Global analyzer configuration applies to C# compiler inputs; it does not
control XML, JSON, or Markdown editor formatting.

## Architectural review

Compiler analysis does not decide whether a service boundary is appropriate,
a nested type is justified, or a directory has a coherent responsibility.
Consumers must also follow these engineering requirements:

- Design services around replaceable abstractions and register them with
  standard `IServiceCollection` extension methods.
- Use full descriptive words even when an abbreviation is outside the analyzer
  vocabulary; language analysis cannot prove that every name is meaningful.
- Keep directories narrowly owned by a feature or subsystem.
- Prefer immutable, concurrent, atomic, partitioned, or message-passing designs.
- Handle exceptions meaningfully; syntactically nonempty catches still need
  review.

The analyzers inspect authored C# source, including the C# written in Razor
files (see [Razor components and views](#razor-components-and-views)). Other
generated code and implementation inside referenced assemblies are excluded.
Conversion analysis detects boxing represented in Roslyn operations; it is not
an allocation profiler or an inspection of every lowered intermediate-language
instruction. Framework signatures are not rewritten. Do not pass value types to
an untyped framework API even if a particular implicit boxing path is outside
static coverage.

## Member separation and ordering

Adjacent methods require at least one blank line, including expression-bodied and interface methods.
Comments, XML documentation, and attributes stay attached to their declaration. Existing blank lines
and newline styles are preserved. This rule does not add padding inside method bodies.

Member ordering follows StyleCop's kind order: fields, constructors, finalizers, events, enums,
interfaces, properties, indexers, operators, methods, structs, classes, and delegates. Records follow
their class or struct kind. Within each kind, order by public, internal, protected internal,
protected, private protected, then private; next by const, static, then instance; next members fixed
once construction ends before settable ones, so a readonly field or a get-only, `init`, `required`, or
computed property comes before a writable field or a property with a `set` accessor; finally by
case-sensitive ordinal name. Overloads with equal keys retain their relative order. Each partial
declaration is ordered independently.

Members that share every key but the name form a bucket, and the blank lines between members follow
the buckets, as statement groups do:

```csharp
private readonly byte[] _localPrivateKey;
private readonly byte[] _sessionKey;

// Filled in as the handshake goes on.
private byte[]? _remotePublicKey;
private byte[]? _sharedKey;

/// <summary>Gets the role of the peer at the other end.</summary>
public RemotePeerRole With { get; }

public void Reset() { }
```

Single-line fields, properties, and events of one bucket sit together with no blank line between them.
One blank line separates buckets, and every method, constructor, nested type, and member that spans
lines or carries XML documentation or attributes stands alone. A comment line opens a new group with
the blank line above it, and within its bucket it heads a section: the members written below it stay
below it, sorted by name, so the comment can say what they are for. A group holds at most four
members (`NETAGENTS0040`); a longer run needs comment lines above its parts. The space after the
opening brace belongs to `NETAGENTS0023`.

Sorting keeps the relative order only where it is observable. Initializers run in written order, so
those that run code (a call, an object creation) keep their order among themselves, and when any
initializer reads another member of the type, every initializer of that phase, static or instance,
keeps its order. Initializers that only read constants, literals, or constructor parameters sort
freely. Fields and properties keep their written order in structs, types annotated with
`StructLayout`, and types that serializers read: those marked `[DataContract]`, `[Serializable]`,
`[ProtoContract]`, or `[MessagePackObject]`, and those with a member carrying a `Json…`, `Xml…`,
`[DataMember]`, `[Column]`, or `[ProtoMember]` attribute. Types containing preprocessor directives are
excluded from ordering so region, conditional compilation, nullable, and warning boundaries remain
intact. Comments and attributes move with their member.
